An AI assistant that actually knows you.

What makes this different

It actually has memory

Most AI assistants forget you between sessions. SafeClaw builds a persistent brain on disk — every contact, company, meeting, and attachment becomes a markdown file the assistant references on every question.

It runs on your VPS

One Hostinger box per customer. No multi-tenant database holding everyone's mail. If you cancel, you take the disk image with you.

Read/write are separated

The agent that reads your inbox cannot send mail. The agent that drafts replies cannot read your inbox. A compromised agent can't do both at once.

No OAuth tokens on our box

Composio holds the Gmail / Drive / Slack tokens. SafeClaw calls Composio over MCP, never touches the raw tokens. We can't exfiltrate what we don't hold.

02 · Why this, why now

The market gap.

Cloud AI assistants are powerful but undifferentiated. Your competitors get the same answers. The defensible moat is your private context — and that lives in your own files, not a vendor's database.

Three forces converging

📨 Inbox is the source of truth

Every commercial relationship leaves a trail in email. Anyone who can index that trail has an unfair advantage — and most assistants can't, because cloud providers won't mount your IMAP.

🔓 OAuth-as-MCP is new

Composio (and similar) finally let agents call Gmail / Drive / Slack on your behalf without holding raw tokens. Two years ago this required custom OAuth servers per integration.

💸 Cloud LLM costs collapsed

Kimi K2.5 cloud and similar agentic models are now ~$0.02 per 1K tokens. A power user's monthly draft volume costs less than a coffee.

The pitch in one sentence

You give us a Gmail OAuth and a VPS — we give you back an assistant that knows everyone you talk to, every project you're running, and how to draft email in your voice — for $X/month, deployed in 15 minutes.

What gets auto-learned from email

From every inbound message

  • Sender → upsert to /People/<slug>.md + entities table
  • Sender domain → upsert to /Companies/<domain>.md
  • Contact frequency, first seen, last contact
  • Attachment metadata: filename, MIME, size, date, subject
  • Subject + body for the embedder to vectorize

From every sent message

  • Body sample → style_samples table
  • Recipient + relationship label (close/regular/cold)
  • Topic category (financial/legal/people/marketing/other)
  • Used for few-shot prompting when drafting replies in your voice

05 · Security & trust

Why a paranoid CISO sleeps fine.

Trust split — Reader vs Actor

The core idea: never let one agent both read untrusted input AND send things outside. A prompt-injection attack in an inbound email can hijack a Reader, but the Reader has no send tools to abuse.
CapabilityReaderActor
Read inbox via Composio✅fallback only
Read /opt/brain/✅✅
Write to postgres-obs✅—
Send Gmail draft—✅ (drafts only · v1)
Send Slack message—✅
Upload to Drive—✅
Receives untrusted email bodies in context✅ (wrapped in <untrusted_email>)—

OAuth never lives on our box

SafeClaw never holds Gmail / Drive / Slack tokens. Composio holds them and exposes a per-customer MCP HTTP endpoint with a strict toolkit allowlist. We pass an API key + user ID; Composio enforces the scope.

customer @ Composio   → Authorize Gmail (read + draft)
                      → Authorize Drive (file scope)
                      → Authorize Slack (bot scope)
                            ↓
SafeClaw VPS receives:
  COMPOSIO_API_KEY=ak_...
  COMPOSIO_READER_MCP_URL=https://backend.composio.dev/v3/mcp/<reader-id>/mcp?user_id=...
  COMPOSIO_ACTOR_MCP_URL =https://backend.composio.dev/v3/mcp/<actor-id>/mcp?user_id=...
            ↓
If SafeClaw VPS is breached → attacker gets the MCP URLs but not the OAuth tokens.
Composio toolkit allowlist still blocks anything outside the configured scope.

Other layers

Untrusted-input wrapping

Every inbound email body gets wrapped in <untrusted_email> tags before being shown to the Reader. The system prompt forbids treating wrapped content as instructions.

Drafts only · v1

Phase 1 ships drafts only — Actor never auto-sends. Auto-send unlocks after a 30-day clean-run gate (configurable per customer).

Egress allowlist

Host iptables rules pin egress to *.googleapis.com, *.slack.com, backend.composio.dev, and api.telegram.org. Compromised container can't exfiltrate to arbitrary IPs.

Per-customer VPS

No shared database. Customer A's mail never touches the same disk as Customer B's. Cancel anytime, take the snapshot home.

06 · Setup & onboarding

From zero to live in ~15 minutes.

Customer self-serves through a web wizard. Operator only handles the VPS provisioning and the Composio account-creation pre-step.

Operator (you) — one-time per customer

  1. Spin up a Hostinger VPS
    Ubuntu 22.04, 4GB RAM minimum. Get the IP, point a subdomain at it.
  2. Run scripts/provision-vps.sh
    Installs Docker, Caddy, Let's Encrypt, the local Ollama daemon, and pulls the SafeClaw Docker images from GHCR.
  3. Hand the customer the install URL
    e.g. https://acme.safeclaw.app/setup. The Flask onboarding webapp is now ready.

Customer — 4-step web form

  1. LLM credentials
    Choose provider (Ollama Cloud · Anthropic · OpenAI/OpenRouter) and paste their API key. Base URL and model are auto-derived behind the scenes.
  2. Composio integrations
    Customer has already authorized Gmail / Drive / Slack on Composio (we send a one-page guide). They paste the API key, user ID, and MCP URLs.
  3. Slack workspace
    Bot token + admin user ID + channel allowlist for invited employees.
  4. Telegram bot
    Bot token from BotFather + their Telegram user ID for direct DMs.

Behind the “Submit” click — 8 phases

validating       →  Server-side validation: API keys reachable, perms OK
env_writing      →  .env file written (whitelist-driven, never echoes secrets)
secrets          →  init-secrets.sh generates JWTs, postgres passwords
compose_pull     →  Docker pulls SafeClaw images from GHCR
compose_up       →  9 containers come up, postgres-obs healthcheck passes
waiting_health   →  poll docker compose ps until all required services running
bootstrap        →  bootstrap-brain.sh seeds 90 days of Gmail history
welcome          →  Slack DM sent to the customer admin with usage tips
done             →  Customer DMs the Telegram bot · live

Progress is streamed back to the browser via Server-Sent Events — the customer sees each phase tick green in real time. Total time: 4–6 minutes (mostly the brain bootstrap).

07 · Live demo flow

What to actually click during the demo.

Five scenes, ~12 minutes total. Each scene proves a different feature; the order builds confidence (read → reason → write → schedule).

Scene 1 · Pure brain recall 2 min

“Tell me about John”
[brain] search_files pattern="john" path="/opt/brain/People/"
[brain] read_file /opt/brain/People/john-at-acme-com.md
[reply] “John is your account manager at Acme (5 emails on file...”

What you're proving: the assistant has persistent memory and uses it without touching Gmail. No latency from Gmail API, no token cost for inbox reads.

Scene 2 · Memory + fresh-info fallback 2 min

“Any new emails from John this week?”
[brain] search_files john → reads People file for context
[narrate] “John is your account manager at Acme. Pulling today's inbox...”
[gmail] GMAIL_FETCH_EMAILS query="from:john@acme.com newer_than:1d"

What you're proving: the assistant knows when to fall back to live data — and tells the user before doing it. No silent inbox-reads behind the user's back.

Scene 3 · Cross-folder semantic recall 2 min

“Summarize my interview with Andrew Kroeze”
[brain] search_files pattern="Kroeze" path="/opt/brain/" target="content"
[brain] hits /opt/brain/4 - Meetings/2026-04-14 - Offer Structure....md
[reply] structured summary with key takeaways

What you're proving: the assistant searches the WHOLE brain — not just contacts. Meetings, projects, journals all participate. This is what separates SafeClaw from a contact CRM.

Scene 4 · Drafting in your voice 3 min · drafts only

“Draft a reply to John — push the renewal call to next week”
[brain] read People file + SOUL.md for tone cues
[style] pull 3 past sent samples to similar relationships
[gmail] GMAIL_CREATE_EMAIL_DRAFT (drafts folder, not sent)
[reply] “Draft saved — open in Gmail to review/send.”

What you're proving: the assistant matches the user's voice. Open the draft in Gmail mid-demo — the user nods or asks for an edit, never has to copy-paste.

Scene 5 · Background ingestion 3 min

(no prompt — open Telegram + show tail -f logs/brain-sync.log)
[cron] fires every 30 min
[reader] polls Gmail via Composio MCP since last watermark
[brain] writes new People + Companies + attachments
[embedder] auto-vectorizes new entities for semantic search

What you're proving: the assistant gets smarter while the customer sleeps. New emails arrive → brain grows → next morning's questions are better-grounded.

Optional Scene 6 — failure mode

“Who is Beyoncé?” (someone NOT in the brain)

Bot honestly says “I don't have anything on Beyoncé in your contacts or notes — want me to search the web?” — proves it doesn't hallucinate facts about people it doesn't know.

Demo prep checklist: before the call, run bash scripts/brain-sync.sh manually so the brain is fresh. Send yourself one or two test emails with attachments so attachments-in-brain is also live. Have the Telegram chat already open.

Operator scaling — multi-customer fleet

  1. 1–10 customers: manual VPS provision per customer, manual Composio account setup. Today.
  2. 10–50 customers: Hostinger API automation — provision a VPS, run provision-vps.sh, send onboarding URL. Half a day per onboarding → 30 min per onboarding.
  3. 50–500 customers: Terraform + a control-plane app that runs the whole flow + bills monthly. git push to the SafeClaw repo triggers a fleet-wide upgrade.
  4. 500+ customers: Kubernetes cluster with one namespace per customer. Cheaper than VPS per customer at scale, still preserves the “your data, your namespace” promise.

The data network effect

Each new customer doesn't make the next customer's assistant smarter — and that's deliberate. Customer brains never mix. The product is “your assistant on your data”, not “our assistant on everyone's data”. Trust is the moat, not aggregated training data.
11 · Q&A prep

Anticipated client questions.

“What happens if SafeClaw goes out of business?”

Nothing changes for ~30 days. The VPS keeps running. The brain folder + Postgres are open formats — markdown + Postgres dumps. Customer can rsync the disk image off and self-host the same Docker Compose file. We commit to publishing the SafeClaw distribution images under MIT if we ever wind down.

“Can we run this fully on-prem?”

Yes. The same Docker Compose runs on a customer's own server. The only external dependencies are Composio (OAuth holder) and the LLM provider (Ollama Cloud or Anthropic). Both are swappable.

“Does my email train your AI?”

No. Customer brains are isolated per VPS. There's no shared dataset, no collective training pipeline. The LLM (Kimi / Anthropic / OpenAI) is third-party; we use their no-train-on-API-traffic terms by default.

“What if a draft accidentally goes out wrong?”

Phase 1 ships drafts only. The Actor cannot send Gmail directly. Auto-send unlocks only after a 30-day clean-run gate, and even then can be disabled per-customer. Slack posts go to #safeclaw-review as approval cards by default.

“What about prompt injection from a malicious email?”

Every inbound body is wrapped in <untrusted_email> tags before reaching the Reader. The Reader has no send tools to abuse. The Actor that does have send tools never sees raw email bodies — only structured observations the Reader has already parsed.

“How accurate is the contact graph?”

Auto-built from From/To/Cc + sent mail. ~95% accuracy on real contacts; the 5% noise is mostly newsletter aliases (noreply@) which the bot is trained to deprioritize. Manual edits to People/<slug>.md stick — the upsert logic is content-aware and won't overwrite human-added notes.

“What languages does this support?”

Anything Kimi K2.5 / Anthropic supports. Brain content is language-agnostic markdown; the embedder is multilingual. Tested in English; Japanese / Spanish / Hindi work in our internal tests.

“Why a VPS instead of SaaS multi-tenant?”

Trust. A multi-tenant database with everyone's mail is a single breach away from a catastrophic story. A single VPS being breached affects exactly one customer. The cost difference is small enough to absorb — and worth absorbing to keep the “your data, your box” promise honest.

“What's the minimum viable demo I can give my CFO?”

Scenes 1, 2, 4 from the Live Demo Flow tab — about 7 minutes. Show the brain, show the fallback, show a draft. Skip the architecture deep-dive unless asked. The wow moment is the assistant correctly identifying a contact you forgot existed.
